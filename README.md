## 1. 这是什么？给谁用？

**RoboCup 3D 仿真组**要求你写一个程序，控制一支**人形机器人足球队**，在物理仿真器里
和其他队伍踢足球。你需要自己解决：

| 问题 | 学术名词 | 难度 |
|------|---------|------|
| 机器人怎么迈腿走路？ | 步态生成 / 行走引擎 | ★★★ |
| 我怎么知道自己在球场哪儿？ | 定位 Localization | ★★★★★ |
| 球滚出视野了怎么办？ | 状态估计 / 搜索 | ★★ |
| 我们三个谁去抢球？ | 动态角色分配 | ★★★ |
| 队友站哪儿不挡路？ | 队形 Formation | ★★★★ |
| 怎么不停下来就踢球？ | 移动中踢球 / RL | ★★★★★ |

**本仓库不教你怎么拿冠军**（那需要一两年），本仓库解决的是更前置的问题：

> 让一个从没接触过机器人的本科生，在**一周内**看懂这个比赛在干什么，
> 在**两周内**跑起来自己的第一个能走能踢的 agent。

## 2. 五分钟上手（零安装）

### 前置要求

**只需要 Python 3.8+**（Windows / macOS / Linux 都行）。
不需要 numpy、不需要 MuJoCo、不需要显卡、不需要联网。

```bash
# 1. 克隆（如果 GitHub 慢，见 docs/01-环境安装.md 里的镜像方案）
git clone <本仓库地址>
cd robocup3d-prep

# 2. 跑闭环仿真（零依赖，直接跑）
cd code
python demo_sim.py

# 3. 看 ASCII 动画版
python demo_sim.py --cycles 400 --render

# 4. 跑 20 场基准测试，得到一个「分数基线」
python demo_sim.py --bench 20
```

**Windows 用户也可以用：**

```powershell
cd code
python demo_sim.py --cycles 1500
```

### 然后打开 3D 可视化

直接**双击** `tools/walkviz/index.html`（用 Chrome / Edge 打开即可）。

你会看到一个 3D 小人走路，右侧有滑块可以实时调步态参数。
**把「左右摆胯」拉到 0，它会告诉你「会摔倒」** —— 这就是稳定性问题的直觉来源。

### 你会看到什么

```
==============================================================================
 RoboCup3D 新手 Demo —— 闭环仿真（自研极简仿真器，零依赖）
==============================================================================
 开始比赛：1500 周期 = 30.0 秒仿真时间

 比赛结束 —— 统计报告
 最终比分          : 3 : 0
 各球员统计：
 球员          踢球次数       行走距离(m)      摔倒次数      状态切换
 0              4         12.83         0        32
 关键事件：
   t=2.6 球员0 射门 球速=6.5m/s
   t=20.5  ⚽⚽⚽ 我方进球！ 比分 1:0
```

### 分层设计：为什么这样分？

这是本仓库最重要的设计思想，也是真实比赛程序的架构：

```
┌─────────────────────────────────────────────┐
│  team.py      多智能体：谁去抢球、谁防守      │  ← 战术层
├─────────────────────────────────────────────┤
│  agent.py     单智能体：状态机               │  ← 决策层
│               （站起来/找球/跑位/对准/踢）    │
├─────────────────────────────────────────────┤
│  walk.py      运动原语：走 / 转 / 踢         │  ← 控制层
├─────────────────────────────────────────────┤
│  core.py      接口约定：Percept / Command    │  ← 通信层
├─────────────────────────────────────────────┤
│  仿真器       物理引擎 + 裁判 + 传感器        │  ← 环境（你不用写）
└─────────────────────────────────────────────┘
```

**每一层只和相邻层说话。** 这样：
- 你想用强化学习替换「行走引擎」→ 只改 `walk.py`，其他不动
- 你想用 RL 替换「决策层」→ 只改 `agent.py`
- 仿真器从自研换成真 MuJoCo 服务器 → 只改 `core.py` 的传输部分

## 4. 三个必须先搞懂的概念

### 概念 1：Agent 的一进一出

比赛程序干的事，本质上就一句话：

```python
while True:
    percept = server.receive()        # 服务器告诉我：我看到了什么
    command = my_brain.decide(percept) # 我想干什么
    server.send(command)               # 告诉服务器：关节转多少度
```

`percept`（感知）里有什么：

| 字段 | 真实协议名 | 含义 |
|------|-----------|------|
| `joint_angles` | HJ (Hinge Joint) | 每个关节现在多少度 |
| `foot_pressure` | FRP (Force Resistive) | 脚底压力（判断有没有着地） |
| `gyro` / `accel` | Gyro / Accelerometer | IMU，判断身体歪没歪 |
| `observations` | See | 看到球 / 球门 / 队友 / 对手 |
| `messages` | Hear | 听到的队友喊话（**带宽极小！**） |

> ⚠️ 感知器的准确名称在不同仿真器版本里不一致（上表是 SimSpark 时代的常见叫法）。
> **2026 起请以 `rcssservermj` 官方文档为准。**
> 本仓库的代码**只依赖「信息类别」不依赖字段名**，
> 所以换到真服务器时只需改传输层映射，业务逻辑一行不动。

`command`（指令）里有什么：**只有关节角度**。
你所有的智能，最后都必须变成一串角度数字。

### 概念 2：为什么定位这么难

看看下面这个例子。左边是真实球场，右边是机器人**实际看到**的东西：

```
   真实球场                          机器人看到的
+---------------------------+              /
|      |           |        |             /
|      |     O     |        |         ---+
|      |           |        |
+---------------------------+
```

机器人只被告知「我面前有一段白线」，但**不知道这是边线还是中线**。
于是它必须问：*「我要把自己旋转、平移成什么样，才能让眼前这些线最好地和球场地图重合？」*

这就是定位问题的本质 —— 一个**搜索 + 匹配**问题。

资料调研里的论文《6D Localization and Kicking》就是解决这个的，效果：**定位误差降低 97%**。

### 概念 3：走路的本质是「周期性的正弦波」

看 `tools/walkviz/walk.py` 里的这一个函数：

```python
def _foot_trajectory(self, phase):
    x = 0.5 * self.p.step_length * math.sin(2 * math.pi * phase)  # 前后
    z = self.p.step_height * math.sin(math.pi * (phase / 0.5)) if phase < 0.5 else 0  # 抬脚
    return x, y, z
```

两条腿的 `phase` 相差 0.5，就走出路来了。
**所有复杂的行走引擎，本质都是在这个骨架上加料。**

|------|------|--------|

## 8. 重要提醒：2026 年规则大改

这是**整个备赛中最容易踩的坑**，务必让全队知道：

| 项目 | 以前（≤2025） | 2026 起 |
|------|--------------|---------|
| 物理引擎 | SimSpark（自研） | **MuJoCo** |
| 服务器 | `rcssserver3d` | **`rcssservermj`** |
| 通信协议 | SPADES | 新的 Python 生态接口 |
| 机器人模型 | Nao | **T1 / K1** 等人形 |
| 规则类 | — | `SSim2026Rules` |

**后果**：网上搜到的绝大多数教程、博客、代码库都是 SimSpark 时代的，
**代码抄过来直接跑不起来**。

**正确做法**：
1. 先确认你要用的代码库有没有适配 2026 规则（看它最后一次 commit 时间）
2. 老代码只读**思想**（状态机怎么设计、定位怎么做），不要读实现
3. 认准官方服务器文档：<https://robocup-sim.gitlab.io/rcssservermj/>

## 9. 常见问题 FAQ

<details>
<summary><b>Q: 我们完全零基础，来得及吗？</b></summary>

来得及，但要**分工**。建议 3~5 人：
- 1 人负责环境 + 服务器搭起来（最苦，但最容易出成果）
- 1~2 人负责行走引擎 / 运动控制
- 1 人负责定位与状态估计
- 1 人负责战术与角色分配 + 文档

第 1 周全员一起跑本仓库的 demo，建立共同语言。
</details>

<details>
<summary><b>Q: 需要什么配置的电脑？</b></summary>

- **本仓库的 demo**：任何能跑 Python 的电脑，包括 10 年前的笔记本。
- **真仿真器（MuJoCo）**：建议 16GB 内存 + 独立显卡（训练 RL 才真正需要显卡）。
- **纯 CPU 也能跑推理**，只是慢。训练时可以租云 GPU。
</details>

<details>
<summary><b>Q: 必须会 C++ 吗？</b></summary>

不必须。2026 年新服务器是 **Python 生态**（rcssservermj 本身是 Python 包），
所以 Python 队伍有优势。但 C++ 代码库更多、性能更好，可以后期再学。
</details>

<details>
<summary><b>Q: 强化学习是不是必须的？</b></summary>

**不是。** 很多队伍用纯规则状态机也能打进决赛阶段。
RL 的优势在「移动中踢球」「快速奔跑」这种人类手调不出来的动作上。
建议：**先用状态机跑通全流程，再挑最弱的一环用 RL 替换。**
</details>

<details>
<summary><b>Q: 为什么 demo 里要自己写一个仿真器，而不是直接用真的？</b></summary>

因为**真仿真器装起来会劝退一半人**（依赖、编译、显卡驱动）。
先用零依赖的简化世界把算法层调通，再上真引擎 —— 这是所有机器人团队的开发顺序。
而且简化世界跑得极快（140 倍实时），方便你快速做实验。
</details>

<details>
<summary><b>Q: 网上说 FCPCodebase 很好，为什么不能用？</b></summary>

它是 SimSpark 时代为 Nao 机器人写的，2026 年换成 MuJoCo + T1/K1 之后，
底层通信协议和机器人模型全变了。**读它的架构可以，直接跑不行。**
</details>

## 10. 贡献与协作

这个仓库的价值在于**持续更新**。建议每人在自己电脑上：

```bash
git checkout -b feature/你的名字-改进点
# 改代码
git add .
git commit -m "feat: 改进踢球对准逻辑，进球率从 60% 提升到 85%"
git push origin feature/你的名字-改进点
# 然后在 GitHub 上开 Pull Request
```

详细的 Git 操作（含中文乱码、大文件、密码误提交等坑）见 `docs/01-环境安装.md` 第 5 章。

**每次改完 agent，请务必跑一次基准测试并把结果写进 PR 描述：**

```bash
python demo_sim.py --bench 20
```

这就是 RoboCup 的标准工作方式：**用数字说话，而不是用感觉。**
