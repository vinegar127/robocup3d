# 04 · 开源代码库分析：该抄哪个、怎么抄

> 核心结论先说：**代码方面能找到的基本都是 base code（基础框架），

## 1. 先搞清楚一件事：2026 年哪些能用

**这一步没做，后面全是白费。** 因为 2026 年换了物理引擎
（SimSpark → MuJoCo），大量老代码库**直接失效**。

### 判断一个代码库能不能用，只问三个问题

```
问题 1：它最后一次 commit / release 是什么时候？
        → 2025 年之前的，基本是 SimSpark 时代的，不能直接用

问题 2：它的 README 里提到 MuJoCo / rcssservermj 吗？
        → 没提到 = 老架构

问题 3：它依赖 rcssserver3d 吗？
        → 依赖 = 老架构。新的是 rcssservermj
```

> 💡 **养成这个习惯**：打开任何一个 GitHub 仓库，
> **第一眼看的是「最后一次提交时间」**，而不是 star 数。
> 在快速变化的技术领域，**新鲜度 > 流行度**。

## 2. 代码库逐个分析

### ✅ 可用的（2026 时代）

#### 1. ApolloCodebase —— 推荐起点

| 项目 | 内容 |
|------|------|
| 地址 | <https://github.com/XiangruiJiang/ApolloCodebase> |
| 语言 | C++ |
| 定位 | **2026 年冠军队公开的 baseline** |
| 适合谁 | 有 C++ 基础，或者愿意学 C++ 的队伍 |

**为什么推荐**：
- 这是**当前规则下**的代码，不存在兼容性问题
- 是**冠军队伍的 baseline**，说明它的架构经过了实战检验
- 有一个明确的起点，不用从零设计架构

**要注意**：
- C++ 学习曲线比 Python 陡
- 「baseline」意味着它**主动降低了竞技水平** ——
  不要指望跑起来就能赢，它的价值是给你一个能跑通的骨架

**怎么用**：
```bash
git clone https://github.com/XiangruiJiang/ApolloCodebase
# 先读架构，再读实现。重点看：
#   1. agent 主循环在哪里？周期是多少？
#   2. 感知怎么解析？指令怎么发送？
#   3. 决策部分是怎么分层的？
```

#### 4. RoboViz —— 必备的可视化工具

| 项目 | 内容 |
|------|------|
| 地址 | <https://github.com/magmaOffenburg/RoboViz> |
| 语言 | Java（你不需要改它，只要会用） |
| 定位 | 3D 可视化调试工具 |

**这是唯一一个「无论规则怎么变都必须装」的工具。**

| 功能 | 说明 |
|------|------|
| 实时观看比赛 | 连到 RoboCup 3D server，显示球场、球员、球的运动 |
| 播放录像 | `--logMode` 打开指定 log 文件，回放已结束的比赛 |
| **调试绘制** | agent 可以在场上画线、画文字 |

> ★ **最后一条功能被严重低估**。
> 你可以在代码里让 agent 把它「以为」的球位置、自己的定位结果、
> 当前状态机的状态画在场上 ——
> 这比看日志快 10 倍，是真正的调试利器。**务必学会。**

**建议：不要试图运行它，只读它的架构。**

## 3. 推荐路线（零基础队伍）

**不要一上来就 clone 一个大代码库然后试图读懂它 —— 那会劝退所有人。**

推荐这个顺序：

```
┌─ 第 1 步：用本仓库建立概念（1 周）─────────────────────┐
│  跑通 code/demo_sim.py，读 code/agent/agent.py         │
│  在 tools/walkviz/index.html 里调参数玩                 │
│  目标：建立「感知 → 决策 → 动作」的肌肉记忆             │
└───────────────────────────────────────────────────────┘
                        ↓
┌─ 第 2 步：读架构，不读实现（1 周）─────────────────────┐
│  读 magmaRelease 和 FCPCodebase 的【目录结构】和 README │
│  目标：知道一个完整球队程序有哪些模块                   │
│  ★ 不要 clone 下来编译！只读文档和目录                 │
└───────────────────────────────────────────────────────┘
                        ↓
┌─ 第 3 步：上手真工具（2 周）───────────────────────────┐
│  装 rcssservermj + RoboViz                             │
│  抄 BahiaRT-MuJoCo-base（Python）或者 ApolloCodebase   │
│  目标：让一个 agent 连上服务器，屏幕上出现一个站着的机器人│
└───────────────────────────────────────────────────────┘
                        ↓
┌─ 第 4 步：替换模块（长期）─────────────────────────────┐
│  用你自己的实现，逐个替换掉 baseline 里的模块：          │
│  先换最简单的（踢球逻辑）→ 再换难的（定位、行走）        │
│  目标：每一周都有可量化的进步                           │
└───────────────────────────────────────────────────────┘
```

### 为什么第 3 步是「抄」而不是「写」

因为**从零写一个能连上服务器的 agent，需要先搞懂协议、序列化、
网络、生命周期管理** —— 对零基础队伍来说，这些「非核心」工作
会吃掉你 80% 的时间，而你真正想学的东西（决策、控制）一点没碰。

**先用 baseline 站住脚，再优化。** 这是效率最高的路径。

## 4. 怎么「抄」代码才是合规的

**RoboCup 明确允许使用开源代码和参考他人工作，但要求注明。**

### 必须做的事

| 事项 | 说明 |
|------|------|
| **检查许可证** | GPL 的代码有传染性！用了 GPL 代码，你的项目可能也必须 GPL。商用/闭源要注意。MIT / Apache-2.0 最宽松。 |
| **在技术报告里注明** | 用了哪个仓库、哪个版本/commit、用了哪部分 |
| **保留原始版权声明** | 不要删掉别人文件头的版权注释 |
| **在 README 里列出致谢** | 本仓库的 README 就有一个「参考与致谢」章节 |

### 绝对不能做的事

| 行为 | 后果 |
|------|------|
| 直接提交别人的代码，声称是自己写的 | **学术不端，取消成绩** |
| 删掉别人的版权声明 | 违反许可证，法律风险 |
| 把 GPL 代码混进闭源项目 | 许可证冲突 |

### 建议在技术报告里这样写

```markdown
## 致谢与参考

本队伍的程序基于以下开源项目开发：

- ApolloCodebase (https://github.com/XiangruiJiang/ApolloCodebase),
  commit a1b2c3d, MIT License
  使用了其 [具体的模块/思路]

- 本仓库的行走引擎参考了 XXX 论文的方法 §3.2，
  但为独立实现。

所有第三方代码的使用均遵守其原始许可证。
```

> 💡 **一个反直觉的建议**：**大方地承认你用了别人的代码。**
> 评委见过太多队伍，你藏不住的，而且「基于开源项目并做了这些改进」
> 是一个完全正当、甚至是值得肯定的技术路线。
> 假装从零开始然后被发现，才是真正的灾难。

## 5. 自己写 vs 用别人的：一个决策框架

新手最常见的困惑：**「这个模块我该自己写还是找现成的？」**

用这个表决策：

| 情况 | 决策 | 理由 |
|------|------|------|
| 通信协议、网络序列化 | **用现成的** | 纯粹的工作量，学不到核心技术 |
| 场地几何、坐标系转换 | **用现成的** | 同上，而且是 bug 高发区 |
| 可视化工具 | **用现成的（RoboViz）** | 重写一遍毫无意义 |
| **行走引擎** | **先用来跑通，再自己改** | 核心技术，长期要自己掌握 |
| **定位** | **必须自己写** | 这是 3D 仿真最难、最有价值的部分 |
| **决策 / 状态机** | **必须自己写** | 这是「你的队伍」和别人的区别所在 |
| 角色分配 / 队形 | **必须自己写** | 多智能体的核心，也是论文的贡献点 |

**规律**：

```
越靠近「机器人怎么思考」→ 越要自己写
越靠近「机器怎么通信」   → 越要用现成的
```

> 💡 一个实用的判断方法：
> **问自己「如果我用现成的，技术报告里能写出什么贡献？」**
> 如果答案是「写不出东西」，那这个模块就应该自己写。
