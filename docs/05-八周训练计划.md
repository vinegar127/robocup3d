# 05 · 八周训练计划

> **用法**：队长直接把这个表发给队员，每周一分配任务，周末验收。
> 每一项都有**可验收的交付物** —— 没有交付物就不算完成。
>
> 本计划假设：零基础、每周每人投入 8~12 小时、3~5 人团队。

---

## 总览

| 周 | 主题 | 核心交付物 | 难度 |
|----|------|-----------|------|
| [1](#第-1-周建立共同语言) | 建立共同语言 | 全员跑出 `3:0` 的 demo | ★ |
| [2](#第-2-周读懂代码) | 读懂代码 | 一份参数实验记录 | ★★ |
| [3](#第-3-周真工具上手) | 真工具上手 | 服务器 + RoboViz 跑起来 | ★★★ |
| [4](#第-4-周第一次连接) | 第一次连接 | 屏幕上出现站着的机器人 | ★★★★ |
| [5](#第-5-周动起来) | 动起来 | 能走到指定点 | ★★★★ |
| [6](#第-6-周找到球并踢出去) | 找到球并踢出去 | 能进一个空门 | ★★★ |

> ⚠️ **第 4 周到第 7 周是最容易「卡死」的阶段**。
> 很多队伍在第 4 周第一次连接服务器失败后就放弃了。
> **对策**：提前约定「卡住超过 3 小时就在群里求助」，
> 不要一个人死磕一整天。

## 团队分工建议

```
                    ┌─────────────┐
                    │   队长      │
                    │  统筹+文档  │
                    └──────┬──────┘
                           │
        ┌──────────────────┼──────────────────┐
        ▼                  ▼                  ▼
  ┌───────────┐     ┌───────────┐     ┌───────────┐
  │ 环境&基建 │     │ 控制&运动 │     │ 感知&决策 │
  │           │     │           │     │           │
  │ 装服务器  │     │ 行走引擎  │     │ 定位      │
  │ 装RoboViz │     │ 转身      │     │ 状态机    │
  │ 构建脚本  │     │ 起身      │     │ 角色分配  │
  │ CI/工具链 │     │ 踢球动作  │     │ 队形      │
  └───────────┘     └───────────┘     └───────────┘
     1 人              1~2 人             1~2 人
```

**为什么这样分？** 因为这三块的**依赖关系最弱**，可以并行推进：
- 环境组不依赖任何人，可以立刻开始（而且**最容易出成果**）
- 控制组只需要仿真器，不需要决策逻辑
- 决策组可以在本仓库的 `demo_sim.py` 里先开发，等服务器好了再接

> 💡 **给零基础队伍的提醒**：**让最不熟悉技术的人去做环境组**。
> 因为装环境是「跟着文档做」的事情，能快速建立信心和成就感，
> 而且环境组是整个队伍的地基 —— 这个位置被卡住，全队都动不了。
> 千万不要让最强的人去做环境然后自己去写算法。

## 第 1 周：建立共同语言

**目标**：让所有人的脑子里有同一幅图 ——
「RoboCup3D = 感知 → 决策 → 动作 的循环」。

### 任务清单

- [ ] **全员**按 `docs/01-环境安装.md` 装好 Python + Git + VS Code
- [ ] **每人**运行 `python scripts/setup_check.py`，确保 0 个 FAIL
  - ⚠️ 注意：本地跑的时候可能因为路径问题有几项 WARN，**FAIL 才算阻塞**
- [ ] **每人**跑通 `python code/demo_sim.py --cycles 1500`，看到进球
- [ ] **每人**跑 `python code/demo_sim.py --cycles 400 --render`，看 ASCII 动画
- [ ] **每人**双击打开 `tools/walkviz/index.html`，
      拖动「左右摆胯」滑块到 0，观察提示变化
- [ ] **全员一起**读 `README.md` 第 4 节（三个必须先搞懂的概念）
- [ ] 建群、建共享文档、确定分工

### 交付物（验收标准）

| 交付物 | 验收方法 |
|--------|---------|
| 环境可用 | 每人截图 `setup_check.py` 的输出 |
| 跑通 demo | 每人贴一次 `--bench 20` 的输出 |
| 观察报告 | 每人用 5 句话回答：「为什么把摆胯调到 0 会摔倒？」 |

> 💡 **最后一项很重要**。它检验的不是记忆力，
> 而是你**有没有真的理解「重心」这件事**。
> 答案提示：机器人走路时重心必须落在支撑脚构成的支撑面内，
> 摆胯就是把重心移到支撑脚那一侧。

### 常见卡点

| 卡点 | 处理 |
|------|------|
| `python` 命令找不到 | `docs/01-环境安装.md` E01 |
| `Activate.ps1` 禁止运行 | E02 |
| pip 下载极慢 | 换清华源，见第 10 章 |
| 中文乱码 | E20 |

## 第 2 周：读懂代码

**目标**：从「能跑」到「知道为什么这么跑」。

### 任务清单

- [ ] 按顺序读这四个文件（**不要跳**）：
  1. `code/agent/core.py` —— 先看接口约定（Percept / Command）
  2. `tools/walkviz/walk.py` —— 再看走路怎么实现
  3. `code/agent/agent.py` —— 然后看状态机怎么决策
  4. `code/demo_sim.py` —— 最后看闭环怎么跑起来
- [ ] **每人至少做 3 个参数实验**，比如：
  - 把 `MotionConfig.kick_range` 从 `0.65` 改成 `1.0` 和 `0.3`
  - 把 `GaitParams.step_length` 改大改小
  - 把 `SoccerField` 的场地尺寸改掉
  - 把 `MiniSim` 的 `fov`（视野角度）从 120 改成 60，看效果
- [ ] 每个实验都跑 `python demo_sim.py --bench 20` 记录数字
- [ ] 回答这些问题（写进共享文档）：
  - 为什么 `agent.py` 里「看不见球」的判断要放在「我不是最近的球员」**前面**？
  - `walk.py` 里两条腿的相位差是多少？为什么是这个值？
  - `Command` 里为什么只有关节角度，没有「向前走 1 米」这种指令？

### 交付物

一份**参数实验记录表**，格式如下：

| 改动 | 改前 | 改后 | 场均进球（20 场） | 我的解释 |
|------|------|------|-----------------|---------|
| kick_range | 0.65 | 1.00 | 2.92 → 2.10 | 踢球范围太大，球员会「远距离空踢」，浪费周期 |
| fov | 120 | 60 | 2.92 → 0.85 | 视野变窄后找不到球，大量时间在 search 状态 |
| …… | | | | |

> ★ **这张表就是 RoboCup 的标准工作方式**：
> 改动 → 用数字验证 → 记录解释。
> 从第 2 周开始养成这个习惯，第 8 周写技术报告时你会感谢自己。

### 常见卡点

| 卡点 | 处理 |
|------|------|
| 看不懂逆运动学 | 不用强求。知道「给脚的位置，反解出关节角」就够了 |
| 不知道 `@dataclass` 是什么 | Python 基础语法，花 20 分钟补一下即可 |
| 改完代码报错 | 用 Git 回退：`git checkout -- 文件名` |

## 第 3 周：真工具上手

**目标**：把真实仿真环境跑起来。**这是全流程最难的一周。**

### 任务清单

- [ ] clone `BahiaRT-MuJoCo-base`（Python，推荐）或 `ApolloCodebase`（C++）
- [ ] 装 `rcssservermj`，启动服务器
  - 官方文档：<https://robocup-sim.gitlab.io/rcssservermj/>
  - ⚠️ 官方文档在 GitLab Pages 上，国内**可能访问不了**。
    如果打不开，让能访问的同学把文档页另存为 PDF 发到群里。
- [ ] 装并启动 **RoboViz**，连上服务器
- [ ] 让 baseline 的 agent 连上服务器（先不改代码，跑原版）
- [ ] 在 RoboViz 里看到球场

### 交付物

| 交付物 | 验收方法 |
|--------|---------|
| 服务器能启动 | 截图服务器启动日志 |
| RoboViz 能连上 | 截图：能看到 3D 球场 |
| baseline 能跑 | 截图：场上有机器人（哪怕是摔倒的） |
| **环境说明文档** | 记录每个依赖的**确切版本号**和安装命令 |

> ★ **最后一项是本仓库反复强调的**：
> 第 4 周之后你一定会需要「在新电脑上重装一遍」，
> 到时候没有这份文档，你会重踩一遍所有的坑。
>
> 建议格式：
> ```markdown
> # 环境说明（第 3 周存档）
> - 操作系统：Windows 11 23H2
> - Python：3.12.8（官网安装包，勾选 Add to PATH）
> - Git：2.47.0
> - rcssservermj：0.1.x（pip install ... 或 git clone + pip install -e .）
> - MuJoCo：3.x
> - RoboViz：1.2.x（Java 需要 17+）
> - 踩过的坑：……
> ```

### 常见卡点

| 卡点 | 处理 |
|------|------|
| 官方文档打不开 | 用镜像/代理，或找同学导出 PDF |
| MuJoCo 装不上 | 大概率 Python 版本太新，换 3.12（见 E06） |
| C++ 编译报错 | 换 Python 版 baseline（BahiaRT）；或装 VS Build Tools |
| RoboViz 闪退 | 检查 Java 版本；用 `java -version` 确认 |
| GPU 相关报错 | **先不管**。跑 agent 不需要 GPU，只有训练 RL 才需要 |

> 💡 **第 3 周的核心心态**：**允许自己「不求甚解」**。
> 你的目标是「让东西跑起来」，不是「理解 MuJoCo 的每一行源码」。
> 遇到看不懂的报错，先搜、先问，**不要试图从原理上搞懂它** ——
> 那是第 5 周之后的事。

## 第 4 周：第一次连接

**目标**：让**你自己写的** agent 连上服务器，屏幕上出现一个站着的机器人。

### 任务清单

- [ ] 读懂 baseline 的通信部分：**感知怎么解析、指令怎么发送**
- [ ] 参考本仓库 `code/agent/core.py` 的 `Percept` / `Command` 设计，
      写你自己版本的接口
- [ ] 把真服务器的协议字段，映射到你的 `Percept`
- [ ] 让机器人**站着不动**（所有关节角设为初始姿态）
- [ ] **加日志**：每个周期打印你要看的几个量

### 交付物

| 交付物 | 验收方法 |
|--------|---------|
| 机器人站着 | RoboViz 里截图上出现一个直立机器人 |
| 日志 | 一份 30 秒的日志文件，包含时间、状态、关键变量 |
| 接口映射表 | 一张表：真协议字段 → 你的 `Percept` 字段 |

### 常见卡点

| 卡点 | 处理 |
|------|------|
| 连不上服务器 | 检查端口、协议、IP；先跑通 baseline 的原始代码作为对照 |
| 连上了但机器人乱抖 | 关节默认角度错了；先全设为 0 试试 |
| 掉线 | 检查主循环是否超时（服务器有周期限制，必须 20ms 内响应） |
| 完全没头绪 | **退回去跑 baseline 的原版，确认环境没问题，再一点点改** |

> 💡 **最重要的建议**：**「先让它不动，再让它动」。**
> 新手总想直接让机器人走路，结果连「站着」都没做对，
> 后面所有问题都会混在一起，无法定位。
>
> **站着不动 = 主循环 + 协议 + 关节映射 全部正确。**
> 这是一个完整的里程碑，值得庆祝。

## 第 5 周：动起来

**目标**：机器人能走到指定点。

### 任务清单

- [ ] 把本仓库 `tools/walkviz/walk.py` 的步态引擎思路，
      或者 baseline 的行走引擎，接进你的程序
- [ ] 实现 `walk(vx, vy)`：向前 / 向后 / 侧移
- [ ] 实现 `turn(w)`：原地转身
- [ ] 实现 `goto(x, y)`：走到场上某个坐标
- [ ] **调参**：让走路不摔
- [ ] 加一个测试：让机器人在场上走一个正方形，用 RoboViz 看轨迹

### 交付物

| 交付物 | 验收方法 |
|--------|---------|
| 能走 | RoboViz 里机器人移动的录屏/截图 |
| 走正方形 | 轨迹近似正方形（允许误差） |
| 步态参数表 | 记录你调出的稳定参数 |

### 常见卡点

| 卡点 | 处理 |
|------|------|
| 一直摔 | 降步幅、抬脚高度、降低躯干高度（参考 walkviz 的稳定性提示） |
| 走不动 / 原地打滑 | 步幅太小，或抬脚太高导致支撑相太短 |
| 走歪 | 左右腿不对称；检查两腿参数是否完全一致 |
| 转身很慢 | 正常。真实人形机器人转身就是慢，这是 3D 仿真的固有限制 |
| 走一会就摔 | 累积误差。需要 IMU 反馈 + 姿态修正（这属于进阶内容） |

> 💡 **调参方法论**：**一次只改一个参数**，并且记录。
> 「我一次改了五个参数结果变好了」= 你什么都没学到，
> 而且下次变差了你也修不回来。

## 第 6 周：找到球并踢出去

**目标**：能进一个空门（对方没有守门员）。

### 任务清单

- [ ] 实现**状态机**（参考 `code/agent/agent.py`）：
      `STAND_UP / SEARCH / APPROACH / ALIGN / KICK`
- [ ] 实现**球的位置记忆**：看不见球的时候，记得球最后在哪
- [ ] 实现**搜索**：完全没线索时，系统地扫描场地
- [ ] 实现**对准**：走到球后面，身体朝向球门
- [ ] 实现**踢球**：一个简单的踢球动作序列
- [ ] **测进球率**：踢 20 次，数成功几次

### 交付物

| 交付物 | 验收方法 |
|--------|---------|
| 能进球 | 录屏：从出发到进球的全过程 |
| **进球率数据** | 「20 次尝试，成功 X 次」 |
| 失败案例分析 | 至少列出 3 种失败模式（踢空、踢偏、被自己绊倒……） |

> ★ **「失败案例分析」比「进球率」更有价值。**
> 第 8 周优化时，你会靠这张表决定先修哪个问题。

### 常见卡点

| 卡点 | 处理 |
|------|------|
| 走到球旁边但踢不到 | 踢球有个「有效距离 + 朝向」窗口，检查你的 `kick_range` 和朝向容差 |
| 踢了但球不动 | 你的踢球判定没触发；加日志看状态机是否真的进入 KICK |
| 球从脚边溜过 | 靠近球时速度太快；实现「接近时减速」 |
| 走到球上摔倒 | 球是障碍物；需要绕行或者慢速接近 |
| 看不见球就不动了 | ★ 检查状态转移顺序（本仓库 `agent.py` 里专门标注了这个坑） |

## 第 7 周：三个人一起上场

**目标**：3v3 完整跑完一场比赛，不崩、不集体摔倒。

### 任务清单

- [ ] 启动 3 个 agent 实例（每个一个进程！）
- [ ] 实现**动态角色分配**：每周期算出谁离球最近
- [ ] 实现**通信**：看得见球的球员把球的位置广播出去
- [ ] 实现**队形**：非抢球的球员去接应/回防位置
- [ ] 实现**开球/进球后的复位**（play mode 处理）
- [ ] **跑完整场比赛**，记录比分

### 交付物

| 交付物 | 验收方法 |
|--------|---------|
| 3v3 能跑 | 录屏：三个机器人同时在场且都在动 |
| 连跑 3 场不崩 | 三次运行都正常结束（不抛异常、不掉线） |
| 分工说明 | 一张图/表说明你的角色分配算法 |
| 比分记录 | 至少 5 场比赛的比分 |

### 常见卡点

| 卡点 | 处理 |
|------|------|
| 三个机器人挤在一起 | 加「避让」逻辑；或让非抢球球员站得更开 |
| 两个都去抢球 | 你的「谁最近」判断有问题（注意：不能共享内存！必须用通信） |
| 通信乱码/丢失 | 检查字符串格式；真实 hear 有带宽限制 |
| 进球后不复位 | 状态机没有处理裁判的 play mode 变化 |
| 一个 agent 崩了全队崩 | ★ **每个 agent 必须是独立进程，且要能容错** |

> 💡 **第 7 周的关键认知**：
> **「三个机器人各自都工作」≠「三个机器人一起工作」。**
> 这是 multi-agent 系统最经典的现象 ——
> 局部最优不等于全局最优，而且**通信是有成本的**。
> 你的机器人广播得越多，带宽越容易爆。
> 想清楚「什么信息值得花带宽去传」。

## 第 8 周：补短板与文档

**目标**：把前 7 周的东西变成**可交付、可复现、有数据**的成果。

### 任务清单

- [ ] **压力测试**：连续跑 20 场，记录崩溃次数和原因
- [ ] **性能剖析**：找出最耗时/最常失败的模块
- [ ] **补最弱的短板**（按第 6 周的失败案例表排序）
- [ ] **写技术报告初稿**（结构见 `docs/02-比赛规则与信息.md` 第 7 节）
- [ ] **整理代码**：删掉调试代码、统一命名、补注释
- [ ] **写 README**：让别人能照着你的说明把程序跑起来
- [ ] **整理第三方代码的许可证说明**

### 交付物

| 交付物 | 验收标准 |
|--------|---------|
| 压力测试报告 | 「20 场中成功 X 场，失败原因分布：……」 |
| 技术报告初稿 | 至少 4 页，包含**数字**（不是只有文字描述） |
| 可复现的 README | 找一个没参与的同学，让他照着跑一遍，能跑通 |
| 许可证清单 | 列出所有用到的第三方代码及其许可证 |

> ★ **「找一个没参与的同学照着 README 跑一遍」** 是检验文档质量
> 最有效的方法。如果他跑不通，评委也跑不通。

                ├─ 方向 A：强化学习替换行走引擎
                │   └─ 参考论文《Learning Humanoid Robot Running》(2021)
                │      端到端 PPO：传感器 → 关节角
                │      需要：GPU、大量训练时间
                │
                ├─ 方向 B：强化学习替换决策层
                │   └─ 参考论文《Deep RL for Humanoid Robot Behaviors》(2022)
                │      RL 输出 (vx, vy, ω)，行走引擎不变
                │      更容易上手，推荐先试这个
                │
                ├─ 方向 C：把定位做扎实
                │   └─ 参考论文《6D Localization and Kicking》(2021)
                │      这是 3D 仿真最难、最有价值的方向
                │
                └─ 方向 D：多智能体协作
                    └─ 参考论文《Designing a Skilled Soccer Team》(2025)
                       角色分配、队形、传球配合
```

**建议顺序：C → B → A → D**。
理由：定位是一切的基础（定位不准，决策再聪明也没用）；
B 比 A 容易见效；D 放在最后因为它的收益依赖前三者的质量。
