## 1. 2D 仿真组：它和 3D 是什么关系

### 1.1 仿真组的分支

RoboCup 的**足球仿真联赛（Soccer Simulation League）**有两个主要分支：

```
              RoboCupSoccer（足球）
                     │
      ┌──────────────┴──────────────┐
      │                             │
 真实机器人联赛                 仿真联赛（纯软件）
 ├─ Small Size (SSL)            ├─ 2D 仿真组
 ├─ Middle Size (MSL)           └─ 3D 仿真组  ← 本仓库
 ├─ Standard Platform (SPL)          （人形双足）
 └─ Humanoid（人形组）
```

> ⚠️ **一个极易混淆的点**：英文缩写 **"SSL"** 在 RoboCup 语境里
> 通常指 **Small Size League（小型组，真实机器人）**，
> **不是** Soccer Simulation League。
> 说「SSL」时务必写全称。

### 1.2 2D 和 3D 的核心差异

| | 2D 仿真组 | 3D 仿真组 |
|---|----------|----------|
| **视角** | 二维俯视平面 | 三维世界 |
| **机器人** | 圆形智能体（无肢体） | **人形双足机器人** |
| **每队人数** | 11 人 | 通常 3 人（早期 5 人） |
| **动作空间** | 小（前进、转身、踢球） | **极大**（20+ 个关节角） |
| **核心难点** | 多智能体协作、不确定性决策 | **双足行走与平衡** + 关节级控制 |
| **上手难度** | 较低 | **明显更高** |
| **难度来源** | 算法与协作 | 物理与控制 |

**为什么 3D 更难？**

因为 2D 里的机器人是「想往哪走就往哪走」，
而 3D 里的机器人**得先学会不摔倒**。

在 2D 中你的决策层输出 `(方向, 力度)` 就结束了；
在 3D 中，这个输出还要经过「行走引擎 → 关节角序列」这一整套转换，
而这一层本身就可能是几年的工作量。

### 1.3 2D 的技术栈（如果你也想了解）

| 项目 | 内容 |
|------|------|
| 服务器 | `rcssserver` |
| 监视器 | `rcssmonitor`（可实时观赛，也可回放 `.rcg` 日志） |
| 客户端库 | `librcsc` |
| 战术基座 | `agent2d` → `HELIOS base`（当前主流） |
| 协议 | **UDP + S 表达式**（文本格式，可读性很好） |
| 默认端口 | 6000 |
| 官方手册 | <https://rcsoccersim.readthedocs.io/> |

**2D 的 agent 主循环（和 3D 概念上完全一样）：**

```
服务器 → (see ...)        我看得见什么（带噪声、有视野限制）
服务器 → (hear ...)       我听到什么（有延迟）
服务器 → (sense_body ...) 我的身体状态（体能、朝向）
        ↓
      你的决策
        ↓
客户端 → (dash 力量 角度)  前进
客户端 → (turn 角度)       转身
客户端 → (kick 力量 方向)  踢球
客户端 → (say 内容)        喊话
```

> 💡 **注意 `see` / `hear` / `sense_body` 这三个消息类型**，
> 它们和 3D 里的感知器（视觉、听觉、本体感觉）是**概念对应**的。
> 所以：**学 2D 的概念，对理解 3D 是有帮助的** ——
> 只是 3D 多了「关节」这个维度。

| 代码库 | 语言 | 说明 |
|--------|------|------|

> ★ **中文入门材料推荐**：
> 中国科学技术大学的《仿真机器人足球：设计与实现》
> <https://wrighteagle2d.github.io/materials/USTC_Material.pdf>
> 这是目前能找到的**最靠谱的中文入门教材**，虽然是 2D 方向，
> 但「多智能体协作怎么设计」这部分完全通用。

### 1.5 你应该学 2D 吗？

| 你的情况 | 建议 |
|---------|------|
| 目标是 3D 仿真组 | ❌ **不要分心去学 2D**，时间不够 |
| 觉得 3D 太难，想先练手 | ✅ 可以花 1 周跑一下 2D，建立「agent 主循环」的概念 |
| 对多智能体协作特别感兴趣 | ✅ 2D 在这个方向研究得更充分（11v11 协作） |
| 想找中文资料 | ✅ 2D 的中文资料**远多于** 3D |

> 💡 **本仓库的位置**：我们专注 3D，但 `docs/03-技术入门.md`
> 讲的「感知 → 决策 → 动作」抽象、以及 `code/agent/` 里的状态机设计，
> **在 2D 和 3D 里是通用的**。这是刻意这样设计的。

## 3. 常见误解清单

> ★ **这一节值得单独读一遍。** 每一条都是真实的坑。

### 误解 1：以为球员之间可以共享内存

❌ **错。** 每个 agent 是**独立进程**。
它们只能通过「看到的」和「听到的」交流，
而 hear 通道**带宽极小、有延迟、有噪声**。

这是 RoboCup 作为 multi-agent 研究平台的核心设定，不是 bug。

✅ **正确做法**：把通信当成有成本的稀缺资源。
想清楚「什么信息值得花带宽去传」。

---

### 误解 2：以为「不摔倒」是天然就会的

❌ **错。** 双足行走是**主动的不稳定** —— 站着不动都在往下倒。
「站着」本身就是一个控制问题。

✅ 这也是为什么本仓库的 demo 里，稳定性是一个要显式检查的指标
（见 `tools/walkviz/index.html` 右侧的稳定性提示）。

---

### 误解 3：以为「三个机器人各自能跑 = 三个一起能跑」

❌ **错。** 这是 multi-agent 系统最经典的现象：
**局部最优 ≠ 全局最优。**

三个各自很聪明的机器人，凑一起可能：
- 全去抢同一个球
- 互相挡路
- 挤在一起

✅ **正确做法**：必须有**显式的角色分配和避让逻辑**。
不能指望「它们自己会协调」。

---

### 误解 4：以为训练数据越多、训练时间越长就越好

❌ **不完全对。** 对强化学习来说，**奖励函数的设计**比训练时长重要得多。

论文 2 里的例子很说明问题：他们发现端到端训练让速度提升了 50%，
**但机器人跑得非常丑**。而且不加「左右对称」先验，
策略自己也会演化成对称的 —— 加先验只是**减少了无效试错**。

✅ **正确做法**：先想清楚「什么样的行为是我想要的」，
再设计奖励去诱导它。不要一上来就开着训练跑三天。

---

### 误解 5：以为论文的方法可以直接抄来实现

❌ **错。** 论文是博士做了几年的成果，你复现不出来，
**也不需要复现**。

✅ **正确用法**：读思路 → 提取核心洞见 → 用最简单的方式实现那个洞见。

例：论文 1 的核心洞见是「垂直姿态要先估，估完问题就简化了」。
你完全可以用一个粗糙的加速度计判断 pitch/roll，就已经赚到了。

---

### 误解 6：以为代码库越新越大越好

❌ **不一定。** GitHub 上 star 多的 RoboCup 代码库，
很多是 **SimSpark 时代**的，2026 年**直接跑不起来**。

✅ **正确做法**：看**最后一次 commit 时间**和**依赖的服务器版本**。
在快速变化的领域，**新鲜度 > 流行度**。

详见 `docs/04-代码库分析.md` 第 1 节的「判断三问」。

---

### 误解 7：以为「人形组冠军」和「3D 仿真组冠军」是一回事

❌ **完全不是。**

| | Humanoid League（人形组） | 3D 仿真组 |
|---|--------------------------|-----------|
| 机器人 | **真实**的双足机器人 | **纯软件仿真** |
| 硬件 | 要买、要修、会摔坏 | 不存在 |
| 平台 | 自定义 | `rcssservermj` |

中文报道经常把两者混为一谈，看到「人形机器人足球冠军」时
**先确认是哪个组**。

---

### 误解 8：以为只要算法好就行，工程不重要

❌ **错。** 工程化能力在这个比赛里权重极高。

真实的教训：
- 程序在组委会环境里**跑不起来** → 技术不合格，直接出局
- 比赛时**崩了一次** → 可能就输掉整场
- 代码**没人接手** → 学长毕业，队伍归零

✅ **正确做法**：
- 第 8 周一定要做**压力测试**（连续跑 20 场）
- README 要能让**没参与的人照着跑通**
- 环境版本要**记录存档**（第 3 周的交付物）

---

### 误解 9：以为需要顶级显卡才能参赛

❌ **错。** **跑 agent 完全不需要 GPU。**

GPU 只有在**训练强化学习**的时候才需要，
而且那通常是备赛后期的事，甚至可以租云 GPU。

✅ 本仓库的 demo 在**任何能跑 Python 的电脑**上都能运行。

---

### 误解 10：以为必须会 C++

❌ **错。** 2026 年新服务器 `rcssservermj` 本身就是 **Python 生态**，
Python 队伍反而有优势。

✅ 不过 C++ 代码库更多、性能更好。可以**先用 Python 起步，后期再学 C++**。

## 4. 一句话总结

```
这个比赛比的不是「谁算法牛」，
而是「谁能把感知、决策、控制、工程、
文档、协作这一整套东西稳定地跑起来」。

────────────────────────────────────
所以：先跑通，再优化。
      用数字说话，而不是用感觉。
      每个模块都要能解释给别人听。
```
