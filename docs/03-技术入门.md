## 1. 系统总览：三个程序，缺一不可

RoboCup 3D 仿真比赛，场上看起来是 6 个机器人在踢球，
实际上是**三套程序在互相通信**：

```
┌──────────────────────────────────────────────────────────────────┐
│                                                                  │
│   ① 球队程序（你写的）          ② 物理仿真器 + 裁判（官方提供）      │
│   ┌──────────────┐              ┌──────────────────────────┐     │
│   │  agent 1     │◄────感知─────┤  rcssservermj (MuJoCo)   │     │
│   │  agent 2     │─────指令────►│                          │     │
│   │  agent 3     │              │  · 创建球场/机器人/球      │     │
│   └──────────────┘              │  · 计算重力/碰撞/关节动力学 │     │
│                                 │  · 推进每个仿真周期        │     │
│                                 │  · 管理比赛状态、执行裁判规则│     │
│                                 │  · 管理受限的队内通信      │     │
│                                 └──────────┬───────────────┘     │
│                                            │                     │
│                                 ┌──────────▼───────────────┐     │
│   ③ 可视化调试工具（别人写的）    │      RoboViz            │     │
│                                 │  · 连接服务器实时看 3D 比赛 │     │
│                                 │  · 播放比赛录像 / log      │     │
│                                 └──────────────────────────┘     │
└──────────────────────────────────────────────────────────────────┘
```

### ① 球队程序 —— 你唯一要写的部分

这就是本仓库提供的东西。每个球员是一个**独立的进程**，各自跑一份 agent。

> ⚠️ **重要认知：球员之间不能共享内存！**
> 三个 agent 是三个进程，它们只能通过「看到的」和「听到的」交流。
> 而 hear 通道**带宽极小、有延迟、有噪声**。
> 这个约束是 RoboCup3D 作为 multi-agent 研究平台的核心价值，
> 也是新手最容易忽略的地方（很多人第一版代码就写成了「全局变量共享」）。

**agent 的主循环，本质上就三行：**

```python
while True:
    percept = server.receive()             # 我感知到了什么
    command = brain.decide(percept)        # 我决定做什么
    server.send(command)                   # 告诉服务器关节角度
```

### ② 物理仿真器 + 裁判 —— 官方提供，你改不了

| 时期 | 引擎 | 服务器 | 机器人模型 |
|------|------|--------|-----------|
| ≤2025 | SimSpark（自研引擎） | `rcssserver3d` | Nao |
| **2026 起** | **MuJoCo** | **`rcssservermj`** | **T1 / K1** |

它负责：创建球场和机器人、计算物理、推进周期、管理比赛状态、
执行裁判规则、收发消息、限制通信。

**你唯一需要理解的是：它每个周期（50Hz，即 20ms）会问你一次「关节角度是多少」。**

### ③ 可视化调试工具 —— RoboViz

**没有可视化工具，你根本没法调试。** 这是新手最容易忽视的关键基础设施。

推荐：[RoboViz](https://github.com/magmaOffenburg/RoboViz)（Java）

| 功能 | 说明 |
|------|------|
| 实时观看 | 连到 RoboCup 3D server，直接显示球场、球员、球的运动 |
| 播放录像 | `--logMode` 可以打开指定 log 文件，回放已结束的比赛 |
| 调试绘制 | agent 可以在场上画线、画文字（这个功能极其有用，务必学会） |

**建议**：第 3 周就要把 RoboViz 跑起来。宁可晚一周写代码，
也不要盲写 —— 你会浪费十倍的时间在「猜我的机器人在干嘛」。

## 2. 赛题拆解：六个子问题

把「让三个人形机器人踢赢足球」拆开，你会得到下面这六个相对独立的问题。
**这正是分工的依据。**

### 问题 1：怎么走路？（行走引擎 / Walk Engine）

**输入**：期望速度 `(vx, vy, ω)`
**输出**：每个关节的角度

人形机器人走路为什么难？因为它是**不稳定**的 ——
两条腿、质心高、支撑面积小。站着不动都在往下倒。

| 方法 | 说明 | 代表工作 |
|------|------|---------|
| **Model-based** | 依赖对动力学的显式建模。你要知道腿多长、重心在哪，把物理先验注入模型（ZMP、LIPM、捕获点） | 传统方法，NASA Valkyrie 等 |
| **Model-free** | 全是数据驱动的，端到端学习出来 | 《Learning Humanoid Robot Running》(2021) |

**关键洞察（论文 2）**：端到端让速度提升了 50%，但**机器人跑得非常丑**。
而且他们发现一个有趣的现象：如果不加「左右对称」的先验约束，
top score 的策略自己也会演化成左右对称的。加了先验只是**减少无效试错、学得更快**。

> 📖 见本仓库 `tools/walkviz/walk.py` —— 一个 200 行的正弦步态引擎，
> 让你 5 分钟建立这个问题的直觉。

### 问题 2：我在哪？（定位 / Localization）

**这是 3D 仿真最难的问题，没有之一。**

机器人能看到两种东西：

| 类型 | 例子 | 难度 |
|------|------|------|
| 有 ID 的标记 | 角旗、球门柱 | 容易 |
| 球场白线 | 边线、中线、禁区线 | **极难** |

**为什么白线难？** 因为服务器只告诉机器人「我面前有一段白线」，
**但不告诉它这是边线还是中线**。

```
   真实球场（map）                    机器人看到的（observation）
+---------------------------+                  /
|      |           |        |                 /
|      |     O     |        |             ---+
|      |           |        |
+---------------------------+
```

于是算法要问：*「我要把自己的坐标系旋转、平移成什么样，
才能让眼前这些线最好地和真实球场地图重合？」*

**这就是一个 搜索 + 匹配 问题。**

**论文 1 的三步解法**（《6D Localization and Kicking》, 2021）：

```
Step 1  估计「天在哪边」
        └─ 先估垂直姿态（pitch/roll）。有了它，问题会大幅简化。

Step 2  Mapping：估 x, y, yaw
        └─ 根据白线生成多个可能的朝向候选
        └─ 再用角旗等 id marker 过滤候选
        └─ ★ 工程 trick：如果无法把候选过滤到唯一，就不更新（宁可不更新，也不要引入错误）

Step 3  Enhance Translation
        └─ 现在知道「这条白线是哪条白线」了
        └─ 于是可以用这个信息反过来提高 x, y, yaw 的精度
```

**效果**：6D 定位误差下降 **97%**。

> 💡 **2D 定位 vs 6D 定位**
> - 2D 定位 = `(x, y, yaw)`：我在哪、面朝哪
> - 6D 定位 = `(x, y, z, roll, pitch, yaw)`：机器人的完整刚体姿态
>
> 为什么要 6D？因为机器人会前倾、后仰、侧歪，只知 2D 不足以控制身体。

### 问题 3：怎么踢球？（Kicking）

传统做法：`walk → stop → kick`（**停下来踢**）
论文 1 的做法：`walk → kick`（**移动中踢**）

**为什么移动中踢很重要？** 因为停下来再踢，从 6 秒降到 1 秒 ——
在比赛里，1 秒的差距就是进球和被抢断的差距。

**怎么训的？** 两阶段训练，外加算法对比：

| 阶段 | 目标 |
|------|------|
| 第一阶段 | 先学会**停下来**踢球 |
| 第二阶段 | 再学**移动中**踢球（以第一阶段策略为起点） |

算法上比较了 **PPO** 和 **SAC**，最终选 **SAC**（Soft Actor-Critic）。

### 问题 4：被撞了怎么不倒？（Push Recovery）

《Learning Push Recovery Behaviors》(2022) 解决的问题：
机器人已经会走了，但我推它一下，怎么让它别摔？

**数学描述**：机器人当前状态 `x_t`，施加外力 `F`，变成 `x_t'`。
恢复 = 找到一个动作 `a`，使状态回到**稳定运动状态**。
> 注意：只要求「稳定」，不要求回到原来状态。

**难点在哪？方向。**

如果你只训练「从前面推」，比赛时被从后面推一下，
因为训练时没见过这种分布，机器人就傻眼了。

**怎么解决？（两个关键技术）**

| 技术 | 做法 |
|------|------|
| **Transfer Learning** | 用「从前面推」的策略做初始化，去训其他方向。前面积累的经验可以复用。 |
| **Imitation Learning** | 每个方向各训一个 expert 策略（应对前推的、后推的……），再做一个「合版」——让**一个**策略同时应对所有方向，而不是路由到不同 expert。 |

**效果**：RL 显著超过 baseline。而且这是**分层**的 ——
它**不是**端到端输出关节角，而是输出高层 `(vx, vy, angle)`，
交给传统 walking engine 执行。

> 💡 **这里有个重要的架构争论**：
> - 论文 2 认为：应该端到端（传感器 → 关节角）
> - 论文 4 认为：端到端有稳定性问题，应该分层（RL 管规划，传统方法管控制）
>
> **两派都有道理。** 论文 3 和 6 都选择了分层。

### 问题 5：我们三个谁去抢球？（动态角色分配 + 队形）

**为什么重要？** 因为足球是 multi-agent 问题。

**最朴素的做法**（也很僵硬）：
```
机器人 1 = 前锋
机器人 2 = 后卫
机器人 3 = 守门员
```
问题：球滚到守门员脚边了，它为什么傻傻守门不去抢？

**进阶做法**：构造一个 **cost 函数**，每周期重新计算谁最适合干什么。
比如 cost = 距离球的远近 + 当前朝向 + 体能 + 位置重要性……

**队形（Formation）**：确定角色之后，每个人具体站哪？
这是个几何问题，也是论文 5 综述里单独列出来的一节。

### 问题 6：模块怎么组合？（Skill-Set-Primitives）

**这是 FC Portugal（2022、2023 冠军队）技术报告的核心贡献。**

**他们发现的问题**：单独训练了很多模块（walk、kick……），
每个单独拿出来都 work，但是**拼接起来就不好用了** ——
动作之间切换时会突变、会摔倒。

**他们的洞察**：

> `walk forward`、`walk sideways`、`turn` 看起来是不同动作，
> 但它们**共享一个共同模式：左右脚交替迈步**。
> 为什么这个公共模式要每个动作各学一次，而不是只学一次然后复用呢？

**所以他们定义了**：

```
        ┌─────────────────────────┐
        │  Step Baseline Primitive │  ← 只学一次：左右脚交替迈步
        └───────────┬─────────────┘
                    │ 所有动作都从这个 baseline 延伸
        ┌───────────┼───────────┬──────────┐
        ▼           ▼           ▼          ▼
     Sprint   Curved Sprint  Sprint-Kick  Omnidirectional Walk
```

**为什么这样更容易切换？** 因为所有动作共享同一个 baseline policy，
动作之间是连续的，不会跳变。

**他们网络有多大？** 很小 —— **1 层，64 个神经元**。
（这说明：**架构设计比模型大小重要得多**。）

**他们 PPO 输出什么？** 6D 姿态 `(x, y, z, roll, pitch, yaw)`，
然后通过 low-pass filter 等传统方法控制运动。

> **为什么不直接输出关节角？**
> 因为输出关节角**自由度太高、动作空间太大**，
> 而输出 6D 姿态再由 **Inverse Kinematics (IK)** 控制，**更符合物理规律**。

**multi-agent 太贵怎么办？**（这一招非常实用）
> 只把**最近的两个机器人**用 3D 精细训练，剩下的简化成 2D 点，以减少开销。

    ├── Dynamic Role Assignment  —— 谁是前锋谁是后卫？

> 你完全可以先用一个粗糙的加速度计判断 pitch/roll，就已经赚到了。

## 4. 技术路线选择：状态机还是强化学习

这是每支新队伍都要做的**第一个重大决策**。

| | 规则状态机 | 强化学习 |
|---|-----------|---------|
| 上手难度 | 低 | 高 |
| 可解释性 | **高**（出问题一眼看出哪个状态错了） | 低（黑盒，进球不了你只能猜） |
| 性能上限 | 中 | **高**（能做出人调不出来的动作） |
| 训练成本 | 几乎为零 | 需要 GPU + 大量时间 |
| 调试难度 | 低 | 高 |

### 推荐路线：**混合式，先状态机后 RL**

```
第 1 阶段：纯状态机跑通全流程
    站起来 → 找球 → 跑位 → 对准 → 踢
    （本仓库的 code/agent/agent.py 就是这一阶段的完整实现）

第 2 阶段：找到最弱的一环，用 RL 替换它
    通常是这两个二选一：
    ├─ 替换【行走引擎】—— 端到端输出关节角（论文 2 路线）
    │  适用：你的行走引擎慢、摔得多
    └─ 替换【决策层】  —— RL 输出高层规划 (vx,vy,ω)
       适用：你的行走还行，但跑位很蠢（论文 3、4、6 路线）
```

**为什么这样分？** 因为这两种替换的**接口不同**：

```
[决策层]──(vx, vy, ω)──►[行走引擎]──(关节角)──►[仿真器]
   ↑                          ↑
   │                          │
 外层 RL 替换这里            内层 RL 替换这里
 (论文 3/4/6 路线)          (论文 2 路线)
```

**如果 RL 替换决策层**：RL 的输入是感知 + 位置，输出是 `(vx, vy, ω)`。
好处是动作空间只有 3 维，学得快；坏处是行走引擎的能力成了天花板。

**如果 RL 替换行走引擎**：RL 的输入是本体传感器（关节角、IMU），
输出是全部关节角（20+ 维）。好处是上限高；坏处是难学、容易摔。

**冠军队伍（FC Portugal）的选择**：分层，RL 输出 6D 姿态 + IK。
这其实是**第三种接口**，介于两者之间，兼顾了物理合理性和表达力。

读到这里，你已经有全局观了。接下来：

1. **跑通 demo**（如果还没跑）：
   ```bash
   cd code
   python demo_sim.py --cycles 1500
   python demo_sim.py --cycles 400 --render
   ```
2. **打开 3D 可视化**：双击 `tools/walkviz/index.html`
3. **读代码**，按这个顺序：
   ```
   code/agent/core.py     ← 先看接口约定（Percept / Command）
   tools/walkviz/walk.py  ← 再看走路怎么实现的
   code/agent/agent.py    ← 然后看状态机怎么决策
   code/demo_sim.py       ← 最后看闭环怎么跑起来
   ```
4. **改一个参数看效果**：把 `agent.py` 里 `MotionConfig.kick_range`
   从 `0.65` 改成 `1.0`，再跑 `python demo_sim.py --bench 20`，
   看场均进球变了没有。
